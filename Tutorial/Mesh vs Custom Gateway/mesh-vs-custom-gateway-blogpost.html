Mesh vs Custom Gateway in Istio VirtualService: The Guide I Wish I Had Before My Exam

A no-jargon walkthrough with a real e-commerce example, an architecture diagram, and three practice labs (basic → medium → exam-level) so you can actually test yourself.

If you've studied Istio for a bit, you've probably seen this line in a VirtualService and quietly skipped over it:

gateways:
- mesh

It looks like a typo. It isn't. mesh is a reserved keyword, not the name of some Gateway resource you forgot to create. Understanding this one field is one of those small things that separates "I can write Istio YAML" from "I actually understand how traffic flows through a service mesh" — and it shows up constantly in certification exams and real production debugging.

By the end of this post you'll be able to:

  • Explain what the gateways field in a VirtualService actually does
  • Explain the difference between mesh and a custom Gateway
  • Know exactly when to use one, the other, or both
  • Solve three practice labs, from basic recall to exam-level troubleshooting

Let's start from zero.

1. Quick refresher: what does a VirtualService even do?

Think of a VirtualService as a routing rulebook. It says things like "if a request comes in for reviews.example.com, send 90% of it to version 1 and 10% to version 2."

But a rulebook is useless until you say who it applies to. Does it apply to:

  • Traffic coming from the public internet, through your ingress?
  • Traffic between your own microservices, inside the cluster?
  • Both?

That's exactly what the gateways field controls.

2. The three ways to fill in gateways:

ValueWhat it meansWhen traffic is affected
(omitted)Defaults to meshInternal, sidecar-to-sidecar traffic only
meshReserved keywordInternal, sidecar-to-sidecar traffic only
my-custom-gatewayName of a Gateway resource you createdOnly traffic passing through that specific ingress/egress Gateway
[my-custom-gateway, mesh]Both, listed togetherBoth internal AND external traffic, using the same rules

This is the whole concept. Everything else in this post is just making sure it sticks.

3. Deep dive: the mesh keyword

Every pod in an Istio mesh gets a sidecar proxy (Envoy) injected next to it. When Service A calls Service B directly — no ingress gateway involved — that call goes through both sidecars. This is the "mesh" traffic path.

When you write gateways: [mesh], you're telling Istio: "apply this routing rule to calls that happen sidecar-to-sidecar, inside the mesh."

Key exam fact: if you don't specify gateways at all, Istio assumes mesh. This trips people up constantly — they create a VirtualService, attach it to nothing explicitly, and then wonder why their external users never see the new routing rule. The answer: it was mesh-only the whole time.

4. Deep dive: the custom Gateway

A Gateway resource is a separate object that configures the load balancer at the edge of your mesh — ports, protocols, TLS certs, hostnames. It's the front door.

apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: reviews-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "reviews.example.com"

On its own, a Gateway just opens a port and says "I'll accept traffic for this hostname." It doesn't know where to route it internally — that's still the VirtualService's job. You connect the two by naming the gateway inside the VirtualService's gateways field.

5. Why would you ever need both at once?

Here's the real-world scenario that makes this click.

Business use case: canary rollout of a Reviews microservice

You work on an e-commerce platform. The reviews-service (star ratings and comments) is used in two very different ways:

  1. External shoppers browsing the site hit it through the public website → traffic enters via your ingress gateway.
  2. Internal services — like product-service, which needs review counts to render a product card — call reviews-service directly, sidecar to sidecar, entirely inside the cluster.

You're rolling out reviews-service v2 (a UI/data-format change) and want to canary it carefully: 10% of all traffic, no matter where it comes from, should hit v2.

If you only bind your VirtualService to the custom gateway, internal calls from product-service will bypass your canary rule completely and go straight to whatever the default routing is — meaning your "10% canary" isn't actually 10% of real traffic, it's 10% of external traffic only. Bugs in v2 could still hit every internal caller at full volume. That's a dangerous blind spot.

The fix: bind the same VirtualService to both mesh and your custom gateway, so one set of rules governs every path.

One VirtualService, two traffic sources — same routing rules apply to both.

6. Step-by-step implementation

Step 1 — Create the Gateway (the front door):

apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: reviews-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "reviews.example.com"

Step 2 — Create one VirtualService bound to both entry points:

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews-vs
spec:
  hosts:
  - "reviews.example.com"   # matched for external gateway traffic
  - reviews-service          # matched for internal mesh traffic (k8s short name)
  gateways:
  - reviews-gateway
  - mesh
  http:
  - route:
    - destination:
        host: reviews-service
        subset: v1
      weight: 90
    - destination:
        host: reviews-service
        subset: v2
      weight: 10

Step 3 — Define the subsets in a DestinationRule:

apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews-destination
spec:
  host: reviews-service
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2

Step 4 — Verify from both directions. Curl reviews.example.com from outside the cluster repeatedly, and curl reviews-service from a pod inside the cluster repeatedly. Over enough requests, both should show roughly a 90/10 split. That confirms the same rule is governing both paths.

7. Cheat-sheet: which value do I pick?

Ask "who calls this service?" first — the answer decides your gateways field.

The one-line rule to memorize: hosts says who this VirtualService applies to (which service/domain), gateways says where the traffic is allowed to come from. Get those two mixed up and nothing routes correctly.

8. Practice Labs

🟢 Lab 1 — Basic — Recall check

You inspect a VirtualService and see this:

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: catalog-vs
spec:
  hosts:
  - catalog-service
  http:
  - route:
    - destination:
        host: catalog-service
        subset: v1

Question: No gateways field is present. Which traffic does this rule apply to — external users hitting an ingress gateway, internal mesh traffic, or both?

Click for solution

Answer: Internal mesh traffic only.

Explanation: When gateways is omitted, Istio defaults it to ["mesh"]. This VirtualService only affects calls made sidecar-to-sidecar between services inside the cluster. External users hitting an ingress gateway would be completely unaffected by this rule — they'd fall through to default routing (typically straight to the service, round-robin across all available pods) unless a separate VirtualService is bound to the gateway.

🟡 Lab 2 — Medium — Find and fix the bug

Your team deployed the following, and external users report they still can't reach payments-service through payments.example.com, even though internal services can call it fine.

apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: payments-gateway
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "payments.example.com"
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: payments-vs
spec:
  hosts:
  - payments-service
  gateways:
  - payments-gateway
  http:
  - route:
    - destination:
        host: payments-service
        subset: v1

Question: What's wrong, and how do you fix it?

Click for solution

Answer: The hosts field only lists payments-service (the internal Kubernetes short name). It's missing "payments.example.com" — the external hostname that the Gateway was configured to accept.

Istio matches incoming requests against the hosts list using the Host header. When an external request arrives at the ingress gateway with Host: payments.example.com, Istio looks for a VirtualService whose hosts list contains that exact string. Since it's not there, the request never matches this VirtualService's routing rules — even though the VirtualService is correctly bound to payments-gateway in the gateways field.

Fix:

spec:
  hosts:
  - "payments.example.com"
  - payments-service
  gateways:
  - payments-gateway

Key exam takeaway: gateways controls where the traffic is allowed to enter from, but hosts controls whether this specific request matches this specific VirtualService. Both conditions must be satisfied — binding to the right gateway isn't enough if the hostname doesn't match.

🔴 Lab 3 — Complex (exam level) — Design and debug scenario

You're the platform engineer for orders-service. Requirements:

  1. External users must reach it at orders.example.com through an existing gateway called public-gateway.
  2. Internal services (cart-service, notification-service) call orders-service directly and must always hit v1 — they must never receive canary traffic, regardless of what external users get.
  3. External users should get a 95/5 canary split between v1 and v2.
  4. A junior engineer wrote this single VirtualService to satisfy all three requirements. Identify every mistake and rewrite it correctly.
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: orders-vs
spec:
  hosts:
  - "orders.example.com"
  - orders-service
  gateways:
  - public-gateway
  - mesh
  http:
  - route:
    - destination:
        host: orders-service
        subset: v1
      weight: 95
    - destination:
        host: orders-service
        subset: v2
      weight: 5
Click for solution

The core mistake: binding both mesh and public-gateway to a single set of http routing rules forces the same canary split onto both traffic sources — exactly the trap this post warned about earlier. That satisfies requirement #3 but directly violates requirement #2 (internal callers must always get v1, no exceptions).

You cannot get two different routing behaviors out of one gateways list applied to one http block. You need two separate VirtualServices, each bound to only the traffic source it should control.

Corrected design — two VirtualServices:

# VS #1 — external traffic only, canary split
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: orders-vs-external
spec:
  hosts:
  - "orders.example.com"
  gateways:
  - public-gateway
  http:
  - route:
    - destination:
        host: orders-service
        subset: v1
      weight: 95
    - destination:
        host: orders-service
        subset: v2
      weight: 5
---
# VS #2 — internal mesh traffic only, always v1
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: orders-vs-internal
spec:
  hosts:
  - orders-service
  gateways:
  - mesh
  http:
  - route:
    - destination:
        host: orders-service
        subset: v1
      weight: 100

Why this works:

  • orders-vs-external is bound only to public-gateway, and its hosts list only contains the external hostname — internal callers using the short name orders-service will never match this VirtualService at all.
  • orders-vs-internal is bound only to mesh, and pins 100% of internal traffic to v1, satisfying requirement #2 exactly.
  • Because each VirtualService's hosts list is scoped to only the relevant traffic pattern, there's no overlap or ambiguity about which rule applies where.

Bonus exam trap to watch for: if both VirtualServices had listed both hostnames in their hosts field, Istio would have two VirtualServices claiming the same host — which produces a conflict warning from istioctl analyze and undefined/inconsistent behavior about which rule actually wins. Scoping hosts tightly to match the intended traffic source is just as important as scoping gateways correctly.

9. Key takeaways

  • gateways: [mesh] (or omitting the field) = internal, sidecar-to-sidecar traffic only.
  • gateways: [my-gateway] = only traffic through that specific ingress/egress Gateway.
  • gateways: [my-gateway, mesh] = one set of rules governs both — great for canaries and A/B tests that must be consistent everywhere, dangerous if you actually need different behavior per source.
  • hosts and gateways are two separate filters that both must match — mixing up their roles is the single most common source of "why isn't my traffic routing" bugs.
  • When internal and external traffic need genuinely different rules, don't force one VirtualService to do both jobs — split it into two, each scoped tightly.

If this clicked for you, the fastest way to lock it in is to actually deploy Lab 3's fix in a local Kubernetes cluster (kind or minikube with Istio installed) and watch istioctl analyze and istioctl proxy-config routes confirm the behavior yourself. Reading YAML gets you halfway there — watching real traffic split is what makes it permanent.
